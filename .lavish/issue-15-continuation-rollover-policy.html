Decision first

One router, four outcomes

The router records an evidence snapshot and chooses resume, fresh, rollover, or refusal. A soft threshold may instead produce awaiting_authority; it never manufactures permission to launch or switch owners.

Default route

Fresh Champion. Resume is exceptional and must be cheaper and safer than reloading durable evidence.

Default rollover authority

Await the Summoner. Automatic mode is explicit, stored, same-scope opt-in.

Separation is the safety mechanism

Four rails that never collapse into one

Teardown may finish while a provider thread remains durably resumable. A resumable archive preserves no endpoint, worktree, resource lease, or callsign.

Runtime teardown

Archive exact identity/evidence, close only the proven endpoint, remove only eligible disposable resources, release callsign last.

Does not select future thread routing.

Callsign queue

Select the first compatible available label from one persistent shuffled queue; activated release appends to the tail.

Does not imply historical identity.

Thread continuation

Claim one exact durable archive, verify resume capability, and bind a newly proven cwd/worktree.

Does not preserve old runtime resources.

Context rollover

Evaluate active context health, authority, safe boundary, handoff digest, acknowledgement, and owner fence.

Does not reclaim a historical callsign.

Policy matrix

The exact outcome is explainable

Explicit resume or fresh routes are preserved. An explicit target that fails identity or safety gates refuses; it is never silently replaced by a different route.

same_task_recovery

An interrupted or blocked operation has an exact durable recovery fence and next action.

The follow-up revises or diagnoses the same exact unlanded head, finding set, or receipt.

unresolved_decision_chain

A bounded acknowledged chain already holds the alternatives and evidence references.

Same callsign, repository, broad topic, issue family, or familiarity does not qualify. If the handoff already contains everything required, fresh wins.

Bounded handoff + fenced recovery

A digest is acknowledged before authority moves

The old incarnation stays authoritative through replacement launch and acknowledgement. The one owner switch is the commit point; cleanup follows it and remains independently recoverable.

Champion

One task pointer changes

The same task/scope remains authorized. A new incarnation receives the handoff; no new task is invented.

Shotcaller

One stable Squad pointer changes

Active Champions retain their exact task, thread, worktree, history, and capability bindings. #8 adds guarded Shotcaller drain/cleanup without making Shotcallers eligible for task teardown.

Handoff includes

  • Stable scope/Squad/task/request and old/new incarnation references.
  • Authority, non-goals, policy/config digest, and instruction-drift result.
  • Current state, unresolved work, claims, blockers, next actions, delivery and cleanup obligations.
  • Applicable repository/head and owner-source evidence references with safe new binding proof.
  • Shotcaller active-Champion map, unchanged.
  • Health inputs, decision reason, callsign reservation, rollback point, and expiry.

Handoff excludes

  • Full transcripts or raw context dumps.
  • Secrets, credentials, private endpoints, or browser state.
  • Local absolute paths or adapter-private locators in public events.
  • Arbitrary generated artifacts or unbounded payloads.
  • Any implied merge, deploy, install, cutover, teardown, or new-task authority.
  1. Decide. Persist evidence, reason codes, policy digest, and automatic/awaiting authority mode.
  2. Prepare. Reserve through #13 and create only the replacement's exact runtime/workspace resources. Old owner remains active.
  3. Acknowledge. Replacement proves its identity/binding and acknowledges the exact handoff digest, scope, non-goals, unresolved work, and preserved Champion map.
  4. Commit. Compare owner version + fence; atomically switch task/Squad owner, append one owner_changed, and enqueue recipient effects.
  5. Drain. Predecessor refuses new intake; Champion task cleanup or #8's separately guarded Shotcaller cleanup reuses proof-first actions, receipts, and fences, then releases callsign last.
Crash before commit

Old owner remains canonical. Retry the same fenced commit or abort exact replacement resources. Restore an unactivated callsign reservation to its recorded queue position.

Crash after commit

Never roll ownership back. Recovery rolls forward predecessor drain and cleanup idempotently. At no point may both incarnations accept intake.

Issue #13 supersedes the obsolete issue-#15 candidate

removed

Never-used generations, quarantine queue, hard cooldown, and least-recently-used fallback.

accepted

One persisted shuffled queue; release appends to tail; recency ranks rather than bans; a recent sole compatible candidate remains allocatable.

A resumed thread receives the historical callsign only if the normal #13 allocator selects it. A rebound name is never stolen or aliased; immutable incarnation and thread references preserve history.

Current-state honesty: the generic runtime has a resume method, but Codex does not declare that capability, Herdr/tmux drivers are contract-only, real runtimes remain unverified, and the current task cleanup planner refuses Shotcallers. #8 must preserve those boundaries while adding one unique thread-lineage identity and a Squad-level owner_changed aggregate; it must not disguise the change as an unrelated task/agent event.

Explicit issue questions and accepted candidate answers
QuestionResolution
When is a follow-up related enough?Only with one of three recorded concrete benefits; labels and broad similarity do not qualify.
Does fresh remain the default?Yes. Resume additionally requires exact durable identity, safe binding, healthy context, and reconciled instructions.
Which health signals are reliable?Canonical age/task counts plus declared normalized adapter signals. Raw transcript guesses are excluded.
Does a threshold auto-create a replacement?No by default. Await authority; automatic rollover requires explicit stored same-scope opt-in and a safe boundary.
What if the old callsign was reused?Allocate normally through #13. Never steal, alias, or rewrite historical identity.
How do roles differ?The contract is identical; only the atomic owner target differs: one task or one stable Squad pointer.
