Contention fixed; runtime wiring incomplete

Executive summary

The canonical database was already operating in write-ahead logging (WAL) mode. A foreground supervisor kept a correct WAL connection open. Every newly started supervisor, prompt, or Stop process nevertheless opened SQLiteStorage with request_wal=False. Connection setup then issued PRAGMA journal_mode=DELETE, which requires an exclusive database lock.

The open supervisor made that maintenance operation unsafe. Stop returned a safe retry message, while UserPromptSubmit surfaced SQLITE_BUSY. Codex did not automatically resend the rejected prompt, so League had no canonical capture receipt for those bytes.

The installed journal correction passed the real long-lived-supervisor gate without increasing timeouts. That success exposed the next release boundary: stable league assign had only internal phases, the global guide still prescribed retired JSON writers, the Shotcaller could not query exact retained untriaged bodies, and a default Champion sandbox could not open the canonical League root.

The successor adds one league request turn process that emits exact intake, atomically accepts model-authored triage/claims/routing, stays open without a transaction while the model works, atomically accepts answers/results and delivery effects, returns the full obligation boundary, and exits. It also adds one recoverable league assign run and only the exact canonical state root as an additional Champion writable root.

UserPromptSubmit still only captures and wakes. It never rewrites the owner body, injects control text, chooses a semantic split, or starts the turn process.

Not resolved yet. Resolution requires one exact installed disposable flow from capture and explicit triage through visible launch, transition, Garen delivery, cleanup, callsign release, zero active residue, and SQLite integrity.

Exact technical root cause

  1. The canonical database had established WAL mode.
  2. A foreground supervisor held a long-lived WAL connection.
  3. src/league/canonical_watcher.py opened each new supervisor, prompt, and Stop connection with request_wal=False.
  4. src/league/sqlite_store.py translated that flag into PRAGMA journal_mode=DELETE on every connection.
  5. WAL-to-DELETE requires an exclusive database lock.
  6. The active supervisor prevented that mode change, so SQLite returned busy during connection setup.
  7. Prompt identity, prompt capture, obligation counting, and Stop generation logic were never reached.

This is a system-boundary defect, not an operator error. The supervisor was behaving correctly; the hot connection incorrectly attempted a maintenance operation.

Why prior canaries missed it

  • The earliest canary covered identical retry deduplication, not different consecutive Garen prompts.
  • The 0.2.8 canary proved source identity without a long-lived supervisor.
  • The 0.2.9 test modeled a short write transaction, not connection initialization against established WAL.
  • Some synthetic stores established DELETE before concurrency, so request_wal=False requested no actual mode change.
  • Model-visible delivery was observed, but model receipt is not canonical capture evidence.

User impact and containment

User impact

  • An ordinary prompt was rejected before League captured it.
  • Codex did not automatically resend the rejected hook event.
  • The prompt remained queued or stuck from League's perspective.
  • Stop could not settle through normal supervision.

Immediate containment

  • Owner disabled only League UserPromptSubmit.
  • League Stop remained enabled.
  • Supervisor and canonical state were preserved.
  • No direct SQLite edit, history rewrite, or automatic hook re-enable occurred.

Corrective code

  1. SQLiteStorage.for_migration remains the maintenance-only path that may establish WAL or DELETE.
  2. Normal opens issue read-only PRAGMA journal_mode, accept only WAL or DELETE, and validate WAL against SQLite 3.51.3 or newer.
  3. canonical_watcher no longer asks hot supervisor, prompt, or Stop connections to select DELETE.
  4. A focused regression keeps a real supervisor subprocess open while prompt and Stop hook subprocesses open together.
No timeout inflation. The correction removes the conflicting maintenance operation. It introduces no schema migration, prompt rewrite, outbox rewrite, or second canonical store.

Successor runtime wiring

  1. league request turn opens one process/connection and emits exact retained bodies only to the live owning Shotcaller under count and byte bounds.
  2. The model authors every semantic item and routing choice in the same normal reasoning pass and supplies no mechanical fields. The already-open adapter deterministically manufactures IDs, claims, hashes, timestamps, JSON, locators, and arguments.
  3. One begin line atomically commits triage, claims, and routing. The connection holds no transaction while the model works.
  4. One commit line atomically records answers/results and delivery effects, returns the full Stop-equivalent boundary, and exits with phase=committed.
  5. league assign run reserves, marks launching, creates one Herdr tab, starts Codex, observes its generated UUID, verifies identity, activates, and delivers bounded context.
  6. Codex remains workspace-write and receives only the exact canonical League root as an additional writable root.
  7. Unproven launch cleanup remains pending. A blocked settlement requires matching endpoint, runtime, and callsign receipts.
  8. The source guide prohibits legacy writers and per-turn status, unresolved, or supervise polling.

Canonical flow study guide

Prompt → request → dispatch

  1. Hook stores exact bytes/source identity and advances wake generation in one transaction.
  2. One turn process emits bounded exact intake.
  3. Model-authored items become prompt sources, requests, claims, and direct/hidden/Champion plans atomically.
  4. Direct answers/results commit on the same process; cross-Squad route and explicit states retain dedicated commands.

Assignment → transition → outbox

  1. assign run reserves, marks launching, creates the exact endpoint, observes its generated UUID, verifies, activates, and hashes bounded context.
  2. task transition commits task version, event, and recipient outbox together.
  3. A registered watcher owns one wake; otherwise one direct fallback is attempted. Offline delivery stays pending.

Supervision → Stop

  1. Event-driven registration lives outside the active model turn; no status/supervise polling.
  2. User messages outrank material-event waits and rearm the generation.
  3. Stop blocks once while any request, prompt, assignment, Champion, delivery, task, or cleanup obligation remains; an identical retry may allow.

Reconciliation → cleanup → rollover

  1. Fresh preflight hashes every source and permits only exact temporary-snapshot reconciliation; live legacy bytes never change.
  2. Cleanup plans immutable ordered effects. Each action receipt makes crash resume start at the first unreceipted step.
  3. Rollover drains intake, snapshots active Champions, binds/acknowledges a replacement, and atomically advances the owner fence.
